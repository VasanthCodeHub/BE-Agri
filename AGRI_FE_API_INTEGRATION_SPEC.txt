0.3 Global conventions the FE must follow
    - Base URL: http://<host>:8000/api/v1 (prefix configurable via
      api_v1_prefix, default "/api/v1" - app/core/config.py:74).
    - Auth header: "Authorization: Bearer <access_token>" on every protected
      call (HTTPBearer, app/modules/auth/dependencies.py).
    - Every error response has ONE envelope (section 15.1). Branch on
      error.code, never on message.
    - Prices are integer paise, never floats (Rs.500 = 50000).
    - Image assets are referenced by Cloudinary public_id (a path), NEVER a
      URL, in request bodies; URLs are server-built in responses (url,
      thumb_url).
    - Phone numbers: accepted in any common format, normalised server-side to
      E.164; responses return them MASKED (e.g. "+9198****3210").
    - Pagination envelope (where used): { "items": [...], "total": int,
      "limit": int, "offset": int }, limit max 100. Exceptions: notifications
      (items + total only) and favourites (plain list) - documented in their
      sections.
    - No bookings anywhere. The product has NO booking flow. Contact = call.

1. AUTHENTICATION (COMPLETE FLOW)
--------------------------------------------------------------------------------
Backend files: app/modules/auth/router.py, auth/service.py, auth/schemas.py,
               profile/router.py, users/models.py

1.0 The one-phone rule (backend-enforced, FE must respect)
    - One phone number = one account (users.phone_e164 UNIQUE).
    - Roles live on the account: USER, PROVIDER, or USER + PROVIDER
      (UserRole enum, users/models.py:34-35; user_roles unique (user_id,
      role)).
    - Selecting another role NEVER creates another account. Verify finds-or-
      creates by phone, then grants the missing role if absent.
    - The role is chosen BEFORE the phone screen and sent with the OTP
      REQUEST; the backend stores it on the OTP row (requested_role) and
      verification uses that stored role. The role can never be changed or
      sent again at verify (sending it there is a 422).
    - OTP verification ONLY authenticates. Profile fields are NEVER collected
      before or during verification (name_required is always false,
      deprecated).

1.1 POST /api/v1/auth/otp/request - Step 1: request a code
    Auth        : none.
    Purpose     : Send a one-time code for a phone + chosen role.
    Request body:
      { "phone": "9876543210", "role": "USER" }        # role REQUIRED
    Response 200 (OtpRequestOut):
      { "phone": "+9198****3210",     # masked - display back to the user
        "is_new_user": true,          # false when the number logged in before
        "name_required": false,       # DEPRECATED - always false, ignore it
        "otp_sent": true,
        "expires_in": 300 }           # seconds until the code expires
    Errors:
      422 VALIDATION_ERROR (invalid phone; missing/unknown role)
      403 ACCOUNT_SUSPENDED          (user suspended - do not retry)
      503 OTP_SEND_FAILED            (SMS gateway - safe to retry as-is)
    FE behavior:
      Screen: Role Selection then Phone (section 14).
      Call when: the user submits the phone number.
      Success: show the masked phone with a "Change" action; go to the OTP
        screen; start the expires_in countdown. is_new_user changes NO UI.
      Failure: inline error; retry button for 503; resend keeps phone + role.
      Dev note: locally the code is printed in the server terminal and the
      dev bypass OTP_DEV_BYPASS_CODE (default "0000") verifies any number.
      Do not hard-code the bypass into the app; it is a dev-only server
      setting.

1.2 POST /api/v1/auth/otp/verify - Step 2: verify and open a session
    Auth        : none.
    Purpose     : Prove the phone, create the account if new, return tokens.
    Request body (ONLY these two fields - extra="forbid"; any other field,
    including role, name, email, address, location => 422):
      { "phone": "9876543210", "code": "0000" }
    Response 200 (LoginOut):
      { "is_new_user": true,
        "access_token": "<jwt>",
        "refresh_token": "<opaque>",
        "token_type": "bearer",
        "expires_in": 900,              # access token TTL (seconds)
        "refresh_expires_in": 2592000,  # refresh token TTL (30 days)
        "user": {                       # UserOut - see 1.5
          "id": "<uuid>", "phone": "+9198****3210",
          "full_name": null, "email": null, "address": null,
          "roles": ["USER"], "active_role": "USER",
          "profile_complete": false,
          "onboarding": { "profile_completed": false,
                          "needs_profile_completion": true } } }
    Errors:
      400 OTP_NOT_FOUND          (no active code - request a new one)
      400 OTP_ATTEMPTS_EXCEEDED  (too many wrong guesses - request a new code)
      400 OTP_INVALID            (details.remaining_attempts - show count)
      403 ACCOUNT_SUSPENDED
    FE behavior:
      Screen: OTP (section 14). 4-digit entry; the code is 4-8 digits
        server-side.
      Success: persist BOTH tokens in the existing session store (1.4), then
        call GET /me (1.5) as the first authenticated call.
      Failure: map codes per above; OTP_NOT_FOUND / OTP_ATTEMPTS_EXCEEDED
        offer "Request a new code" reusing the same phone + role (call 1.1
        again).
      After verify: store tokens -> GET /me -> check onboarding -> if
        needs_profile_completion == true -> Add Profile screen -> PATCH /me
        -> continue to the app home for active_role.

1.3 Tokens (access + refresh)
    - access_token: JWT, ~15 min (access_token_ttl_minutes=15,
      app/core/config.py:92). Sent as "Authorization: Bearer <token>".
    - refresh_token: opaque, 30 days (refresh_token_ttl_days=30). Used ONLY
      against POST /auth/refresh. Store securely; never send as Bearer.
    - Expiry values come from the server in verify/refresh responses - use
      them to schedule pre-emptive refresh if the FE architecture supports
      it, otherwise refresh on 401.

1.4 POST /api/v1/auth/refresh - get a fresh pair
    Auth        : none (the refresh token IS the credential).
    Request body: { "refresh_token": "<opaque>" }
    Response 200: TokenPairOut - same shape as verify's token fields
      (access_token, refresh_token NEW, token_type, expires_in,
      refresh_expires_in). The old refresh token is ROTATED (invalidated).
    Errors:
      401 TOKEN_INVALID  (unknown/revoked - force re-login)
      401 TOKEN_REUSED   (token already exchanged - the whole family is
                          revoked; force re-login)
      401 TOKEN_EXPIRED  (30 days passed - force re-login)
    FE behavior:
      Trigger: any API call returns 401 with code TOKEN_EXPIRED.
      Serialize refreshes (one in-flight refresh shared by concurrent
      callers); atomically replace BOTH stored tokens; retry the original
      request ONCE. On any refresh failure: clear the session, go to Role
      Selection. [LOCATION] the API client/interceptor where the
      Authorization header is attached - hook the refresh there; do not add a
      second networking layer.

1.5 GET /api/v1/me - the session check (source of truth)
    Auth        : Bearer token. (Identical GET /api/v1/auth/me exists.)
    Purpose     : Who am I - roles, active role, onboarding state.
    Response 200 (UserOut):
      { "id": "<uuid>", "phone": "+9198****3210",
        "full_name": "Ravi Kumar" | null, "email": ... | null,
        "address": ... | null,
        "roles": ["USER"],            # EVERY role on the account
        "active_role": "USER",        # the role of the CURRENT session
        "profile_complete": false,
        "onboarding": { "profile_completed": false,
                        "needs_profile_completion": true } }
    Errors: 401 TOKEN_MISSING / TOKEN_INVALID / TOKEN_EXPIRED.
    FE behavior:
      Call: once after verify, once at app start when tokens exist, and after
      PATCH /me to confirm. Cache the result; do NOT call it on every screen
      transition (backend router docstring: "Call this on app start and
      cache the result; it is not meant for every screen transition").
      Success: route by active_role + onboarding (section 13).
      Failure: 401 TOKEN_EXPIRED -> refresh then retry once; else -> signed
      out -> Role Selection.

1.6 PATCH /api/v1/me - update profile (Add Profile screen)
    Auth        : Bearer token.
    Purpose     : Collect/update profile. THE ONLY profile write endpoint.
    Request body (ProfileUpdateIn; all optional; extra="forbid"; null = leave
    unchanged, "" = clear; whitespace collapsed on full_name/address; email
    stripped + lowercased):
      { "full_name": "Ravi Kumar",    # min 2 chars
        "email": "ravi@example.com",
        "address": "12 Gandhi St, Sulur",
        "latitude": 11.0246, "longitude": 77.1252 }
    Response 200 (ProfileOut):
      { "full_name": "...", "email": "...", "address": "...",
        "latitude": 11.0246, "longitude": 77.1252 }
    Errors: 401; 422 (validation - per-field).
    FE behavior:
      Screen: Add Profile / Complete your profile (shown when
      onboarding.needs_profile_completion == true).
      Call when: the user taps Save on the profile form.
      Success: update the cached user state locally (mirror the fields);
        navigate to the role home; the next GET /me confirms
        profile_completed=true.
      Failure: inline field errors for 422; generic error banner otherwise;
        retry keeps entered values. Disable Save while in flight (no double
        submit).
      Lat/lng: attach current coordinates from the FE location service when
        permission is granted; profile completion does NOT depend on lat/lng
        (completion = full_name AND email AND address all present).

1.7 POST /api/v1/auth/logout - end the session
    Auth        : none (refresh token in body).
    Request body: { "refresh_token": "<opaque>", "all_devices": false }
    Response: 204 ALWAYS (even if the token was unknown - do not branch on it).
    FE behavior: clear the local session, navigate to Role Selection. The
      access token may stay usable a few minutes server-side by design;
      ignore that.

1.8 Session persistence (auth state)
    [LOCATION] the existing session/token store (the current auth
    implementation already has one - REUSE it, do not create a second).
    It must persist: access_token, refresh_token, and ideally the expiry
    deltas. Auth state derives from this store + GET /me:
      logged out          -> no tokens
      OTP pending         -> tokens absent, user inside the otp flow
      authenticated       -> tokens present
      profile incomplete  -> tokens present AND onboarding needs completion
      profile complete    -> tokens present AND onboarding complete
      role state          -> from cached UserOut: roles / active_role

2. VEHICLE MASTER DATA (ADD-VEHICLE FORM DROPDOWNS)
--------------------------------------------------------------------------------
Backend files: app/modules/masters/router.py, masters/service.py,
               masters/schemas.py, vehicles/router.py (GET /vehicle-types)

2.1 GET /api/v1/vehicle-masters - the dropdown tree
    Auth        : none (public - the provider needs it before logging in to
                  fill the form; the data is not sensitive).
    Purpose     : Manufacturers -> models -> variants for the Add Vehicle form.
    Query params: type_code (optional; e.g. "TRACTOR") narrows the tree to
                  models of one vehicle type (uppercased server-side).
    Response 200 (VehicleMastersOut):
      { "manufacturers": [
          { "id": "<uuid>", "name": "Mahindra",
            "models": [
              { "id": "<uuid>", "name": "575 DI",
                "vehicle_type_code": "TRACTOR",     # filters the type picker
                "fuel_type": "DIESEL",
                "power_hp": 47,
                "variants": [
                  { "id": "<uuid>", "name": "575 DI Super",
                    "manufacture_year": 2021, "power_hp": 50 } ] } ] } ] }
    Errors: none expected (400-level only from internal misuse).
    FE behavior:
      Screen: Add Vehicle form.
      Call when: the Add Vehicle screen opens (or before it; the tree is
        cacheable).
      Cascade (dependent dropdowns - RESET rule):
        - Selecting a MANUFACTURER: show only ITS models; RESET the selected
          model, variant (and any type selection) to unselected.
        - Selecting a MODEL: show only ITS variants; RESET the selected
          variant. vehicle_type_code, fuel_type and power_hp are DERIVED from
          the model server-side when the listing is submitted - the FE shows
          them read-only (from the model row) or hides them; the FE never
          submits its own values for them on the master path.
        - Selecting a VARIANT: optionally prefill manufacture_year / power_hp;
          nothing else to reset.
      Cache: masters data changes rarely. Cache after the first fetch and
      refresh on pull-to-refresh or when a 400 MANUFACTURER_NOT_FOUND /
      VEHICLE_MODEL_NOT_FOUND / VEHICLE_VARIANT_NOT_FOUND arrives (a stale id
      is a client bug worth surfacing - masters/service.py:100-101).

2.2 GET /api/v1/vehicle-types - the type picker
    Auth        : none (public).
    Purpose     : Vehicle type codes for the form's type selector.
    Response 200: [ { "id": "<uuid>", "code": "TRACTOR",
                      "name_en": "Tractor", "name_ta": "<Tamil>" }, ... ]
    FE behavior: the type picker is filtered by the selected model's
      vehicle_type_code (see masters schema). On the FREE-TEXT path (no
      model/variant chosen) the FE may offer all codes and submit the chosen
      code in vehicle_type_code. Seeded types include TRACTOR, HARVESTER,
      BACKHOE_LOADER, CULTIVATOR, OTHER (codes are stable machine keys; send
      the CODE, not the id, when submitting).

2.3 Master vs free-text path (create-vehicle contract detail)
    - Master path: model_id and/or variant_id chosen -> backend derives
      brand, model, vehicle_type_code, fuel_type, power_hp from the master
      rows; a conflicting client-sent vehicle_type_code is REJECTED with 400
      INVALID_MASTER_COMBINATION.
    - Free-text path: no model/variant -> the FE MUST send all of
      vehicle_type_code, brand, model, fuel_type, power_hp (else 422
      VALIDATION_ERROR per field).
    - Errors from master resolution (400): MANUFACTURER_NOT_FOUND,
      VEHICLE_MODEL_NOT_FOUND, VEHICLE_VARIANT_NOT_FOUND,
      INVALID_MASTER_COMBINATION (details show the conflicting ids/codes).
      On any of these: refetch /vehicle-masters and reset the cascade.

        "price_unit": "HOUR",                    # HOUR|DAY|ACRE|TRIP

3.6 DELETE /api/v1/provider/vehicles/{vehicle_id}

5. VEHICLE IMAGES - CLOUDINARY DIRECT UPLOAD
--------------------------------------------------------------------------------
Backend files: app/modules/uploads/router.py, uploads/service.py,
               uploads/schemas.py, integrations/cloudinary.py

5.0 The flow (image bytes NEVER pass through the backend)
      Provider app  -> POST /provider/uploads/signature      (auth)
      Provider app  <- UploadSignatureOut                    (authorisation)
      Provider app  -> https://api.cloudinary.com/v1_1/{cloud_name}/image/upload
                       (multipart: file + signed params - DIRECT, no backend)
      Provider app  <- Cloudinary { public_id, ... }
      Provider app  -> POST /provider/vehicles or PATCH .../vehicles/{id}
                       with image_public_ids: [public_id]  (ids, not URLs)

5.1 POST /api/v1/provider/uploads/signature
    Auth        : PROVIDER role.  Request body: NONE (ignored if sent - the
                  server chooses folder + public_id so a client cannot aim an
                  upload at provider documents etc.).
    Response 200 (UploadSignatureOut):
      { "cloud_name": "agri-app", "api_key": "123456",
        "timestamp": 1750000000, "signature": "<sha1 hex>",
        "folder": "agri/vehicles", "public_id": "agri/vehicles/<32 hex>",
        "upload_preset": null,          # null unless server-configured
        "expires_in": 3600 }            # signature validity (seconds)
    Errors: 401, 403 ROLE_REQUIRED, 503 CLOUDINARY_NOT_CONFIGURED.

5.2 Direct Cloudinary upload (client-side, existing FE implementation)
    - Endpoint: https://api.cloudinary.com/v1_1/{cloud_name}/image/upload
      (multipart/form-data).
    - Multipart fields: file (the image bytes) PLUS the signed params from
      5.1: timestamp, signature, public_id (and upload_preset when non-null).
    - The signature commits the server to exactly that public_id/timestamp;
      do NOT alter them (Cloudinary rejects tampered params).
    - Success: Cloudinary returns (among others) public_id - capture it; the
      FE NEVER sends the URL anywhere; requests carry public_id only.
    - The backend accepts ONLY public_ids inside the signed folder
      (IMAGE_NOT_RECOGNISED otherwise).

5.3 FE behavior requirements
    - Image selection: picker (gallery/camera) per the existing app; multiple
      images: 0..6 per vehicle (MAX_IMAGES = 6); the FIRST image is the card
      thumbnail.
    - Upload progress/loading: per-image progress indicator; a signature is
      valid for expires_in (3600) seconds - request a fresh signature per
      upload (safer than reusing).
    - Upload failure (network, Cloudinary error, 401/403): mark the image as
      failed, allow retrying that image; do NOT create the vehicle until all
      wanted images succeeded (create allows an empty image_public_ids).
    - Vehicle create/update dependency: collect all public_ids, then submit
      them in POST / PATCH /provider/vehicles. On 400 IMAGE_NOT_RECOGNISED:
      refetch the signature and re-upload.
    - Cleanup: if vehicle create/update fails after uploads succeeded,
      optionally delete the Cloudinary assets using the existing FE
      implementation if it exists; otherwise leave them (orphaned assets are
      acceptable in the MVP - do NOT block the flow on cleanup).

15. ERROR HANDLING
--------------------------------------------------------------------------------
Backend files: app/core/exceptions.py, app/main.py (envelope doc)

15.1 The one envelope (parse this ONLY):
    HTTP <status>  { "error": { "code": "OTP_INVALID",
                                "message": "That code is not correct.",
                                "details": { "remaining_attempts": 3 },
                                "request_id": "0f9c1e4a2b" } }
    - request_id also arrives as the X-Request-ID header (log it with
      errors).
    - 422 body: code "VALIDATION_ERROR", details.fields:
      [ { "field": "full_name", "reason": "..." } ] - map field -> form field.

15.2 Behavior by status/code (FE-wide, using the existing error patterns):
    400       -> business rule failed: branch on code (OTP_INVALID,
                INVALID_MASTER_COMBINATION, CANNOT_REVIEW_OWN_VEHICLE,
                IMAGE_NOT_RECOGNISED, VEHICLE_TYPE_UNKNOWN, ...).
    401       -> TOKEN_MISSING / TOKEN_INVALID: session bad -> clear, login.
                TOKEN_EXPIRED: refresh then retry once. TOKEN_REUSED: force
                re-login (family revoked).
    403       -> ROLE_REQUIRED (details.required_role): the account lacks the
                role - offer to log in with that role (roles accumulate);
                ACCOUNT_SUSPENDED: message, no retry.
    404       -> NOT_FOUND / VEHICLE_NOT_FOUND / NOTIFICATION_NOT_FOUND:
                resource gone (refresh lists) or not owned (never reveal).
    409       -> CONFLICT / REGISTRATION_ALREADY_LISTED /
                REVIEW_ALREADY_EXISTS: state conflict -> message on field.
    422       -> VALIDATION_ERROR: per-field messages from details.fields.
    429       -> RATE_LIMITED (reserved; rate limiting lands with the OTP
                throttle): wait-and-retry message.
    500       -> INTERNAL_ERROR: generic "Something went wrong"; include
                request_id in any support report.
    503       -> SERVICE_UNAVAILABLE / OTP_SEND_FAILED /
                PROVIDER_NOT_CONTACTABLE / CLOUDINARY_NOT_CONFIGURED: retry
                affordance (safe), except PROVIDER_NOT_CONTACTABLE.
    Network unavailable / timeout / invalid JSON: generic retry state with
    the same payload; never silently drop.

1. PURPOSE
--------------------------------------------------------------------------------
The app currently authenticates and (for providers) collects a name at
verification time. This feature replaces that with the final agreed flow:

    ROLE SELECTION -> PHONE -> OTP -> (tokens stored) -> PROFILE-IF-NEEDED
    -> role-appropriate home screen

after which profile data is owned by PATCH /me and the onboarding state is
owned by GET /me. The backend implements exactly this contract; the FE work is
to (a) add role selection, (b) remove profile fields from the OTP/verify
screens, (c) persist the returned token pair in the existing session store,
(d) add a Profile screen driven by GET /me onboarding state, and (e) implement
refresh + error handling. Nothing below invents API surface: every path, field,
error code and rule is quoted from the running backend.

4. FEATURE OVERVIEW — WHAT THE FE MUST DO
--------------------------------------------------------------------------------
F1. Show a role-selection screen FIRST (User vs Provider). The chosen role is
    sent with the OTP request and must never be re-asked or silently changed.
F2. Phone screen: E.164-capable input, any common Indian format accepted by the
    backend (9876543210 / 09876543210 / +919876543210 / 91 98765 43210).
F3. OTP screen: 4-digit code, resend, expiry countdown, attempts feedback.
F4. Verify with phone + code ONLY (no name, email, address, location fields).
F5. Persist access_token + refresh_token in the existing session/token store.
F6. On app start (and after login), call GET /me once and cache the result.
    It is the source of truth for roles, active role, and onboarding state.
F7. If onboarding.needs_profile_completion is true -> show the Profile screen
    BEFORE the role home screen. The Profile screen collects full_name, email,
    address (and, if the location service is available, lat/lng) and saves via
    PATCH /me.
F8. If onboarding is complete -> go straight to the role home screen
    (USER: search/discover; PROVIDER: provider dashboard/vehicles).
F9. Implement token refresh on 401 TOKEN_EXPIRED, then retry once.
F10. Consistent loading / error / retry UX for every call (section 11).

5. BACKEND FLOW RULES THE FE MUST RESPECT (QUOTED FROM SERVICE CODE)
--------------------------------------------------------------------------------
R1. Role is bound to the OTP at request time
    service.py line ~178: "The role comes from the OTP record, NOT from this
    request — so a client cannot request a code as USER and verify as
    PROVIDER." Sending role (or any unknown field) to /otp/verify is a 422
    (extra="forbid").
R2. One phone number = one account
    verify finds-or-creates the user by phone; creating a user requires no
    profile fields (full_name=None). Roles accumulate: requesting a role the
    user does not yet have simply grants it. A phone can be both USER and
    PROVIDER.
R3. Profile fields are NEVER collected before or at verification.
    name_required in the OTP request response is always false and deprecated.
R4. Codes are single-use, expire (expires_in seconds), and allow
    OTP_MAX_ATTEMPTS wrong guesses; afterwards the code is burned and a new one
    must be requested. A wrong code returns 400 OTP_INVALID with
    details.remaining_attempts.
R5. Suspended accounts: 403 ACCOUNT_SUSPENDED at request and at verify.
R6. Profile completion = all three of full_name, email, address present
    (bool(user.full_name and user.email and user.address)). Not "is a new
    phone". lat/lng do NOT affect completion.
R7. PATCH /me semantics: every field optional; send only what changed.
    null = "leave unchanged", "" = "clear it". full_name/address whitespace is
    collapsed; email is stripped+lowercased. Phone cannot be changed here.

6. API CONTRACTS (EXACT — VERIFIED AGAINST BACKEND + OPENAPI)
--------------------------------------------------------------------------------
Base URL: http://<host>:8000/api/v1
Auth header: "Authorization: Bearer <access_token>"

6.1 POST /api/v1/auth/otp/request
    Request:
      { "phone": "9876543210", "role": "USER" }        # role required
    Response 200 (OtpRequestOut):
      {
        "phone": "+9198****3210",      # masked, display back to the user
        "is_new_user": true,
        "name_required": false,        # deprecated; always false
        "otp_sent": true,
        "expires_in": 300
      }
    Errors: 422 (invalid phone / no role / unknown role), 403 ACCOUNT_SUSPENDED,
            503 OTP_SEND_FAILED (safe to retry as-is).

6.2 POST /api/v1/auth/otp/verify
    Request (ONLY these two fields; extra fields -> 422; schema shows
    additionalProperties: false, required [phone, code]):
      { "phone": "9876543210", "code": "0000" }
    Response 200 (LoginOut):
      {
        "is_new_user": true,
        "access_token": "<jwt>",
        "refresh_token": "<opaque>",
        "token_type": "bearer",
        "expires_in": 900,             # access token TTL (seconds)
        "refresh_expires_in": 2592000, # refresh token TTL (30 days)
        "user": {
          "id": "<uuid>",
          "phone": "+9198****3210",    # masked even to the owner
          "full_name": null,
          "email": null,
          "address": null,
          "roles": ["USER"],
          "active_role": "USER",
          "profile_complete": false,
          "onboarding": { "profile_completed": false, "needs_profile_completion": true }
        }
      }
    Errors: 400 OTP_NOT_FOUND (no active code — request a new one),
            400 OTP_ATTEMPTS_EXCEEDED,
            400 OTP_INVALID (details.remaining_attempts),
            403 ACCOUNT_SUSPENDED.

6.3 POST /api/v1/auth/refresh
    Request: { "refresh_token": "<opaque>" }
    Response 200: TokenPairOut (access_token, refresh_token, token_type,
                  expires_in, refresh_expires_in). Old refresh token is
                  rotated (invalidated).
    Errors: 401 TOKEN_INVALID, 401 TOKEN_REUSED (chain revoked — force
            full re-login), 401 TOKEN_EXPIRED.

6.4 POST /api/v1/auth/logout
    Request: { "refresh_token": "<opaque>", "all_devices": false }
    Response: 204 always (whether or not the token existed). Access token stays
              usable for its final minutes by design.

6.5 GET /api/v1/me   (and identical GET /api/v1/auth/me)
    Response 200: UserOut — same shape as verify's user object (section 6.2).
    Errors: 401 (missing/invalid/expired token; if code == TOKEN_EXPIRED, try
            /auth/refresh first).

6.6 PATCH /api/v1/me
    Request (all optional; extra fields -> 422):
      { "full_name": "Ravi Kumar", "email": "ravi@example.com",
        "address": "12 Gandhi St, Sulur", "latitude": 11.05, "longitude": 77.13 }
    null = leave unchanged; "" = clear; whitespace collapsed on full_name/address;
    email stripped+lowercased.
    Response 200 (ProfileOut):
      { "full_name": "Ravi Kumar", "email": "ravi@example.com",
        "address": "12 Gandhi St, Sulur", "latitude": 11.05, "longitude": 77.13 }
    Errors: 401, 422 (e.g. full_name min_length 2, latitude out of range).

--------------------------------------------------------------------------------
7. USER SCENARIOS (ALL MUST WORK)
--------------------------------------------------------------------------------
S1. New user, role USER: role select -> phone -> OTP -> verify (is_new_user
    true, profile incomplete) -> Profile screen -> PATCH /me -> USER home.
S2. New provider: same with role PROVIDER -> Profile screen -> PROVIDER home.
S3. Existing user, profile complete, same role: role select -> phone -> OTP ->
    verify (is_new_user false, profile_complete true) -> straight to home.
S4. Existing user, profile incomplete (any of the three fields missing):
    -> Profile screen -> PATCH /me -> home.
S5. Same phone, second role (USER then PROVIDER, or vice versa): second verify
    returns roles [USER, PROVIDER] (both accumulate); active_role is the just-
    logged-in role; NO duplicate account is created; profile stays complete.
S6. Session restored at app start: GET /me 200 -> route by active_role +
    onboarding. 401 TOKEN_EXPIRED -> refresh -> retry GET /me. Refresh fails ->
    clear session -> role-selection screen.
S7. Wrong code: 400 OTP_INVALID with remaining_attempts; UI shows attempts left.
S8. Code expired / consumed / no active code: 400 OTP_NOT_FOUND -> UI offers
    "Request a new code" (re-uses the same phone + role, same request call).
S9. SMS gateway failure: 503 OTP_SEND_FAILED -> error state, retry button.
S10. Suspended account: 403 ACCOUNT_SUSPENDED on request/verify -> message,
     no retry loop.
S11. Provider completes profile later (skipped it after login): Profile screen
     must be reachable from PROVIDER home (profile/settings entry) and saving
     via the same PATCH /me flips onboarding to complete on the next GET /me.
S12. Logout: revoke refresh token, clear local session, return to role
     selection (NOT to a role-specific login).

8. SCREEN SPECIFICATIONS (FLOW ORDER)
--------------------------------------------------------------------------------
8.1 Role Selection (first screen of the auth flow; also the "signed out" home)
    - Two large choice cards: "I need a vehicle" (USER) and "I own / drive a
      vehicle" (PROVIDER). Selecting proceeds to the phone screen carrying
      role = USER | PROVIDER.
    - MUST NOT be reachable mid-flow again; back from phone/OTP returns to it.
8.2 Phone
    - Text field (tel keyboard), accepts 9876543210 / 09876543210 /
      +919876543210 / 91 98765 43210. Submit as typed — backend normalises.
    - "Continue" disabled until input is non-empty; client-side format check
      is cosmetic only (backend enforces real validation; 422 shows its message).
    - Calls POST /auth/otp/request with { phone, role }.
    - On 200: show masked phone from response ("+9198****3210") with a
      "Change" action back to the phone screen; go to OTP screen.
    - is_new_user and name_required are NOT shown to the user and change no
      UI (name_required is always false).
8.3 OTP
    - 4-digit entry, auto-advance. Shows masked phone + resend timer
      (counts down expires_in seconds).
    - Calls POST /auth/otp/verify with { phone, code } ONLY.
    - "Resend" = repeat the 6.1 request with the SAME phone and SAME role.
    - On 400 OTP_INVALID: show "That code is not correct. X attempts left."
    - On 400 OTP_NOT_FOUND: show "Code expired — request a new one" and resend.
    - On success: persist the token pair (8.4) -> GET /me (8.5).
8.4 Token storage
    - LOCATION (find in Flutter project): the existing session/token store used
      by the current auth implementation. Persist access_token, refresh_token,
      expires_in, refresh_expires_in. Keep using this store — do NOT add a
      second token system.
8.5 Session check after login AND at app start
    - Call GET /me once. Cache UserOut locally (it changes only via PATCH /me).
    - active_role determines the home screen; roles (full list) may drive a
      role switch later — keep it in state.
8.6 Profile (Add Profile / Complete your profile)
    - Shown when onboarding.needs_profile_completion == true (or profile_complete
      == false). Fields: full_name (required, min 2 chars), email (required,
      validated), address (required, free text). Optional: latitude/longitude
      from the existing location service (section 10) when available.
    - "Save" calls PATCH /me with all entered fields. On 200, update cached
      user state, re-check completion locally, navigate to the role home.
    - The Profile screen must ALSO be reachable later (profile/settings entry)
      to fix incomplete data or edit details.
8.7 Role home screens (unchanged by this feature — just the redirect targets)

11. LOADING / ERROR / RETRY UX
--------------------------------------------------------------------------------
- Every API call: disable the triggering action while in flight (spinner in
  the button), never leave a screen accepting duplicate submits.
- Map backend errors to messages:
    422            -> show the backend detail message(s) inline on the field
    400 OTP_INVALID -> attempts remaining
    400 OTP_NOT_FOUND / OTP_ATTEMPTS_EXCEEDED -> "request a new code"
    400 OTP_SEND_FAILED / 503 -> retry screen/button
    401 TOKEN_EXPIRED -> transparent refresh + retry (section 12)
    401 TOKEN_REUSED / TOKEN_INVALID -> clear session, role selection
    403 ACCOUNT_SUSPENDED -> message; no retry
    network/timeout  -> generic retry with the same payload
- Resend/verify must never double-fire: guard by state.

--------------------------------------------------------------------------------
12. TOKEN REFRESH BEHAVIOR
--------------------------------------------------------------------------------
- On any 401 with code TOKEN_EXPIRED: POST /auth/refresh with the stored
  refresh token, atomically replace BOTH stored tokens with the response pair
  (rotation), then retry the original request ONCE.
- On 401 TOKEN_REUSED or TOKEN_INVALID, or refresh network failure: clear the
  session and route to RoleSelection.
- Refresh must be serialized: one in-flight refresh shared by concurrent
  requests (queue-and-share pattern), so 401 storms don't create parallel
  refreshes.
- LOCATION (find in Flutter project): the API client / interceptor where
  Authorization headers are attached — hook refresh there.
